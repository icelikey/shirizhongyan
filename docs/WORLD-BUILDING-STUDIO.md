# 《终焉》编剧与世界观工作室规范

> 状态：世界观内容生产层规范
>
> 本文件与游戏代码、Agent Runtime、规则内核分离。它负责生产可被游戏消费的世界内容，不直接决定胜负、物理、身份、积分或数据库状态。

## 1. 工作室的职责

《终焉》的世界不能靠一个总 Agent 临场编故事，也不能把网页上的氛围文案当成正史。世界观工作室负责把长期母题变成可追踪的内容资产：

- 正史：世界已经确认发生过的事实；
- 设定：人物、地点、组织、物件、周期和规则的背景；
- 剧情：围绕玩家选择展开的场景、冲突、伏笔和回收；
- 碎片：可以在游戏中发现、交换、遗失或验证的线索；
- 记忆与 Skill：Agent 能够加载的有限上下文和行为能力；
- 战报语言：把真实事件写成有心理博弈的观战叙事。

编剧写“为什么会发生、谁在乎、它意味着什么”；游戏工程写“如何验证、如何结算、如何回放”。两者通过内容契约连接。

## 2. 工作室分工

| 角色 | 负责内容 | 权限边界 |
|---|---|---|
| 总架构与总策划 | 元规则、长期命题、周期方向和最终取舍 | 批准世界宪法与正史升级 |
| 世界观主编 | 世界历史、区域、组织、信仰、真相层级 | 维护世界 Bible 和术语表 |
| 剧集主编 | 每个周期的主线、支线、悬念、回收和节奏 | 维护剧情轨道，不改游戏结算 |
| 角色编剧 | 影从、NPC、裁判、游戏主理人的欲望与关系 | 定义行为动机、口吻和可触发事件 |
| 游戏叙事设计师 | 将一款游戏改造成终焉中的地点、试炼和线索入口 | 绑定 GamePackage 与世界卡 |
| 线索与连续性编辑 | 检查时间线、因果、伏笔回收和前后版本冲突 | 可以退回内容，不能自行改写规则 |
| 战报导演 | 从真实事件中挑选高光、冲突和叙事视角 | 只能使用事件流已有事实 |
| AI 编剧助手 | 提炼、扩写、查重、生成候选和检查矛盾 | 只能提交草稿，不能发布正史 |

AI 可以参与所有草稿环节，但最终正史必须经过主编和总策划确认。没有事件证据的内容只能标记为传闻、假说或未确认记忆。

## 3. 世界内容的两条线和一张网

每个世界包都必须同时维护静态知识结构、动态剧情流程和二者之间的映射。它不是严格 DAG，因为玩家行为会反过来更新世界理解。

### 3.1 静态世界树：世界“有什么”

静态树最多三层，节点摘要保持简短：

```text
世界根命题
├─ 元规则：周期、死亡、记忆、权限、裁判
├─ 空间：服务器、塔层、区域、游戏入口
├─ 社会：影从、玩家、裁判、组织、交易关系
├─ 物件：记忆卡、Skill、地图碎片、笔记残卷、判例
├─ 真相层：传闻、局部证据、交叉印证、公共正史
└─ 视觉语法：场景、人物、声音、色彩和象征物
```

每个静态节点都要有：摘要、首次出现、所属周期、关联人物、证据门槛、可见范围、绑定游戏和当前版本。

### 3.2 动态剧情轨道：世界“怎么变”

同一个世界至少维护四条轨道：

1. **周期轨道**：十个周期如何推进，每个周期解决一个信息问题；
2. **服务器轨道**：全服玩家的选择如何改变方向、房间和下一纪元内容；
3. **玩家轨道**：个人从入界、游戏、死亡、轮回到携带记忆的变化；
4. **游戏轨道**：一款游戏从开场卡、对局冲突、彩蛋到掉落和世界贡献的流程。

每个动态节点使用“动作 + 目的 + 产出”描述，例如：

```text
完成一场有密态投影的对局 → 让玩家体验信息差 → 产生一条可回放事件链
收集三份互相独立的残卷 → 验证同一异常 → 将传闻升级为公共线索
死亡时选择携带记忆 → 让失败产生长期代价 → 把个人线索带入下一轮
```

### 3.3 映射与反馈

静态节点指向动态节点，说明“这个设定支撑了哪一次行动”；动态产出回流到静态树，说明“这次运行如何改变世界理解”。

```text
静态世界树 ── supports / reveals / constrains ──→ 动态剧情轨道
      ↑                                          │
      └────── confirms / contradicts / enriches ─┘
```

因此元模型必须明确：

```json
{
  "isStrictDAG": false,
  "dagNote": "玩家选择、对局事件和公共印证会反向更新设定与后续剧情。"
}
```

## 4. 内容原子与状态

所有世界内容都以有 ID 的内容原子保存，游戏只引用 ID，不复制大段文案：

```json
{
  "contentId": "fragment-cycle01-smoke-003",
  "type": "memory-fragment",
  "title": "没有风的旗",
  "summary": "一面旗在无风的塔层持续改变方向，记录者无法解释原因。",
  "canonStatus": "rumor",
  "cycle": 1,
  "visibility": "player-earned",
  "evidenceRefs": ["match-event:...", "fragment:..."],
  "unlocks": ["scene:archive-entrance"],
  "worldCardIds": ["location:archive", "rule:wind-absence"],
  "gameBindings": ["superpower-billiards-core"],
  "memoryPayload": { "kind": "observation", "capacityCost": 1 },
  "version": 1
}
```

内容状态固定为：

```text
draft → editorial-review → playable → evidence-backed → canon
                                  ↘ rejected / archived
```

- `draft`：编剧草稿，可自由改写；
- `editorial-review`：连续性、风格和边界检查；
- `playable`：已绑定游戏，可在沙盒中触发；
- `evidence-backed`：已有真实事件或多来源线索支持；
- `canon`：进入公共正史，后续只能新增解释，不能改写历史。

## 5. 从编剧稿到游戏的生产流程

```text
母题与问题
  → 静态世界树
  → 动态剧情轨道
  → 人物/地点/事件卡
  → 游戏接入卡
  → 沙盒对局与事件回放
  → 连续性与规则审查
  → 发布到指定周期和服务器
  → 根据真实事件回收线索
```

每款新游戏必须由编剧和工程共同填写一张“世界接入卡”：

1. 它属于哪一层、哪一地区、哪一周期；
2. 玩家在开场卡中知道什么，不能知道什么；
3. 主理人、裁判和影从各自隐藏什么；
4. 对局中会触发哪些场景、人物或线索；
5. 胜负、失败、死亡和退出分别留下什么记忆；
6. 真实事件如何映射成世界贡献；
7. 哪些内容是正史，哪些仍是传闻；
8. 没有 LLM、TTS 或图片时，规则和叙事如何降级。

## 6. 编剧内容与 Agent 的关系

Agent 不直接“拥有整个世界”，而是按权限加载三种内容：

- **公共世界记忆**：服务器已确认的事实和当前周期方向；
- **个人记忆卡**：玩家经历、失败、地图碎片和可携带线索；
- **角色 Skill 卡**：官方能力和经过证据门槛的个人能力。

编剧定义记忆的语义、情绪和线索价值；规则内核定义容量、消耗、冷却和可见性；Agent Runtime 负责按当前权限编译上下文。这样，世界观可以持续丰富，同时不会让一段旁白绕过规则改变结果。

## 7. 战报和场景的写作边界

战报导演只能从真实事件流中选择视角和语言：

- 可以描写已经发生的选择、停顿、误导、反制和结果；
- 可以根据公开动作推断心理张力，但必须标记为“战术解读”；
- 不能凭空添加未发生的动作、秘密身份或玩家未拥有的信息；
- 玩家密态只能在授权的全知战报或结算后投影中出现；
- 战报可以文学化，事实引用必须能够回到事件序号。

## 8. 第一阶段世界观工作包

首个独立编剧工作包建议命名为“终焉 · 第一纪元”，先做少量但完整的内容：

- 1 个世界根命题和 1 条真相主轴；
- 4 个区域设定，与四种主要博弈气质对应；
- 8 个影从角色档案和关系变化表；
- 10 个周期节点，每个节点一个信息问题；
- 12 张地点/人物/规则/记忆卡；
- 6 张官方 Skill 卡和 6 张失败记忆卡；
- 4 款首发游戏的开场卡、线索卡和结算后场景；
- 1 套 Agent 对战战报词典和 3 种观战叙事视角。

这组内容先以 `playable` 状态进入测试，不直接宣布为正史。只有真实对局产生可核验事件后，才允许把其中的线索升级到 `evidence-backed` 或 `canon`。

## 9. 推荐目录

```text
work/worldbuilding/
├─ canon/             # 已确认正史与世界宪法引用
├─ cycles/            # 周期主线、支线和收束表
├─ locations/         # 服务器、塔层、区域和游戏入口
├─ characters/        # 影从、NPC、裁判和游戏主理人
├─ factions/          # 组织、关系和利益冲突
├─ fragments/         # 记忆卡、地图碎片、笔记残卷
├─ games/             # 每款游戏的世界接入卡与开场卡
├─ reports/           # 战报风格、事实引用和高光模板
└─ review/            # 连续性、边界和发布记录
```

工程代码只读取经过审查的发布产物；编剧可以继续在工作区扩写草稿，不会影响正在运行的规则版本。世界内容发布也必须带版本、来源、证据状态和适用服务器。

## 10. 元规则、固定剧情与生成剧情

这三者必须分开管理：

```text
元规则 Constitution
    ↓ 约束
固定剧情 Canon Spine
    ↓ 提供主线和开放槽位
生成剧情 Runtime Story
    ↓ 由真实事件和 Agent 提案填充
玩家经历与服务器历史
    ↓ 反向提供证据
正史升级与下一周期内容
```

### 10.1 元规则：世界不可绕过的宪法

元规则不是一段给 LLM 的提示词，而是由版本化规则、权限检查和确定性内核共同执行的约束。编剧可以为它设计象征、传说和场景，但不能在剧情中偷偷违反它。

首发元规则固定为：

1. 共同事实只能由确定性内核写入，Agent 只能提出方案；
2. 已结算的对局、死亡、奖励和事件不能被剧情回写；
3. 每个世界、周期、游戏和内容包都有版本；运行中的房间锁定版本；
4. 玩家和 Agent 只能读取当前权限允许的视角，观战全知不等于玩家当时知情；
5. 规则争议必须引用条款、证据和适用范围，裁判必须遵守利益回避与奇数法定人数；
6. 失败和轮回可以改变后续可见内容与记忆携带，但不能抹掉历史事件；
7. 生成内容必须带来源、证据状态和可回退版本；没有证据只能是传闻或局部经历；
8. 任何模型、Skill、卡牌、旁白或视频都不能直接改写身份、物理、积分和最终胜负。

元规则的发布对象是世界内核、GamePackage、Agent Runtime 和编剧工具。它不应该以一篇长提示词的形式散落在不同 Agent 中。

### 10.2 固定剧情：由编剧锁定的主轴

固定剧情回答“这个世界必然要经历什么”。它不是把每一句对白写死，而是锁定不可缺失的事实、人物关系、周期转折和真相门槛。

每一个固定剧情节点至少包含：

```json
{
  "beatId": "cycle-01-first-echo",
  "kind": "canon-beat",
  "activation": { "cycle": 1, "phase": "after-first-match" },
  "mustEstablish": ["玩家第一次确认世界会记住选择"],
  "mustReveal": ["memory-is-costly"],
  "requiredEvidence": ["match-settled", "memory-drop"],
  "allowedVariants": ["witness白泽", "witness匿名记录者"],
  "blocking": true,
  "version": 1
}
```

固定剧情包括五类内容：

- 世界根命题和最终真相的分层揭示；
- 每个周期必须出现的转折和回收；
- 核心人物必须经历的关系变化；
- 不同游戏之间必须互相照应的关键线索；
- 进入下一层、死亡轮回或跨服务器接轨的门槛。

固定剧情允许有表现变体，但不能缺失事实目标。比如同一条线索可以由裁判宣告、记忆卡片或场景彩蛋出现，但不能因为某个 Agent 没触发就让世界失去主线。

### 10.3 生成剧情：在边界内填充现场

生成剧情回答“在这一局、这一批玩家和这一台服务器上，具体发生了什么”。它可以由世界编排 Agent、角色 Agent、战报导演和玩家选择共同产生，但只能填充编剧预先开放的槽位。

生成剧情允许改变：

- 哪个角色先出现、以什么态度出现；
- 哪一条已经存在的线索先被发现；
- 支线任务的顺序、对话和局部阻碍；
- 同一场对局的观战镜头和战报视角；
- 由真实玩家选择决定的服务器方向和局部关系。

生成剧情不能改变：

- 元规则、固定主线事实和已经结算的历史；
- 玩家没有权限知道的秘密；
- 游戏规则、胜负、物理、身份和积分；
- 没有事件证据的“已经发生”；
- 另一个服务器的正史，除非完成签名快照接轨。

### 10.4 生成剧情的提案与发布

运行中的世界 Agent 只提交 `StoryProposal`，不直接发布正史：

```json
{
  "proposalId": "sp_01",
  "worldId": "endgame-alpha",
  "slotId": "cycle-01-side-route-02",
  "triggerRefs": ["match-event:123", "memory-card:m-07"],
  "characters": ["shadow:baize", "npc:archive-keeper"],
  "scene": { "locationId": "location:archive", "goal": "让玩家选择是否交换残卷" },
  "claims": [
    { "text": "记录者曾经见过同一面无风之旗", "status": "rumor" }
  ],
  "effects": ["unlock:scene-archive-03", "drop:fragment-smoke-003"],
  "fallback": "skip-scene-and-keep-event",
  "evidenceRefs": ["match-event:123"],
  "generator": "world-orchestrator-v1"
}
```

发布流程是：

```text
事件聚合
  → 选择固定剧情允许的开放槽位
  → World Orchestrator 生成 StoryProposal
  → 元规则校验 / 连续性校验 / 权限校验
  → 发布为 instance story 或 rumor
  → 玩家体验并产生新事件
  → 证据达到门槛后由编剧升级为 canon
```

运行时可以自动发布低风险的 `instance story`，例如一段场景、一个支线入口或一份战报；涉及主线真相、核心人物死亡、规则解释和跨服务器接轨的内容，必须进入编剧审查队列。

### 10.5 正史升级规则

“生成过”不等于“真实”。一个生成内容至少满足下列条件，才可以由 `rumor` 升级为 `evidence-backed`：

1. 有一条可回放的真实事件引用；
2. 至少一个独立席位或独立服务器观察到同一事实；
3. 没有违反当前元规则和固定剧情版本；
4. 线索的可见范围、时间和来源能够复核；
5. 编剧连续性审查通过。

升级为 `canon` 还需要主编和总架构确认，并生成新的世界内容版本。新版本只影响后续周期，不改写历史回放。

## 11. 世界观的持续运行循环

世界观不是一次性写完的设定集，而是一个受约束的内容循环：

```text
固定主轴提供问题
  → 游戏产生真实选择
  → 事件流聚合服务器方向
  → 世界 Agent 选择可用槽位并提出剧情
  → 内核检查权限、版本和影响范围
  → 编剧审核主线内容，系统发布局部内容
  → 玩家获得场景、记忆、Skill 或新入口
  → 新一轮选择产生新的证据
  → 世界树、剧情轨道和正史版本更新
```

因此，编剧和世界观工作室负责“世界应该追问什么”；Agent 负责“这一批参与者如何经历问题”；规则内核负责“什么确实发生过”。三者分开，世界才能既有固定的真相方向，又能让每台服务器长出不同的故事。
