# 终焉：服务器世界与多 Agent 涌现架构

状态：世界层 V1 的确定性聚合契约、数据库持久化和公开读取接口已落地；跨服务器合并仍处于协议阶段，不能把“提案”当成已经合并。

## 1. 世界的基本单位

**一个服务器就是一个世界。**服务器有自己的 `worldId`、规则版本、纪元、公开锚点、世界方向和真相碎片。玩家、真人与 Agent 在这个服务器内参加游戏；他们完成的选择改变这个世界下一纪元的方向。

世界方向不是一个大模型随口生成的主题，而是有限状态集合：

| 方向 | 进入世界的表现 |
|---|---|
| 规则 | 新地点更强调条款、裁判和可复核事实 |
| 发言 | 角色关系、公开辩论和语音事件权重上升 |
| 信任 | 协作、承诺和互惠奖励变得更重要 |
| 断裂 | 异常、背叛和小概率能力链更容易出现 |
| 记忆 | 线索、残卷、轮回和旧事件回声更容易被召回 |

方向只改变下一纪元的内容供给、事件权重和可见线索，不直接篡改已经结算的积分、身份或物理结果。

## 2. 从玩家选择到世界方向

每局游戏仍由自己的规则内核裁定。对局结束后，世界层只接收一条脱敏的 `WorldContribution`：

```text
对局结算
  → 生成公开贡献（方向、规则固定权重、证据引用）
  → 写入 world_contributions
  → 以 eventId / contributionKey / participantRef + gameId 去重
  → 聚合一个世界纪元
  → 形成方向、公共锚点和真相碎片
  → 世界 Agent 编排下一纪元内容
```

这里有三个边界：

1. 同一玩家在同一游戏中的重试、重复点击和 Agent 重连不能重复投票。
2. Agent 的动作数量不能直接变成世界权重；权重由游戏规则固定，默认每位参与者每局一票。
3. 私密身份、未揭晓数字、API Key、完整私聊和裁判内部提示词不进入公共世界状态。

当前确定性实现位于 `app/contracts/worldEmergence.ts`，测试覆盖了重试去重、方向 quorum、真相碎片确认门槛和接轨提案。终局入口位于 `app/api/games/sdk/runtime.ts`，持久化与读取位于 `app/api/queries/worldEmergence.ts`。

当前 V1 的真实接口是：

```text
GET /.well-known/tdg-world.json
GET /world/v1/world/state
```

`/world/v1/world/state` 只返回公共聚合结果：方向计分、独立参与者数量、公共锚点、真相碎片和校验摘要。它不会返回身份、未揭晓数字、完整对话、API Key 或个人工作记忆。服务启动前可运行 `pnpm db:ensure-world-emergence` 幂等创建 `world_contributions` 与 `world_epochs` 两张表。

## 3. “真相”如何涌现

世界真相不是全服票数最多的文案。它需要三层证据：

- **事件证据**：至少有真实结算事件引用它。
- **跨游戏证据**：至少来自两种不同玩法，避免单一玩法偏差。
- **独立参与者证据**：至少三名不同玩家或 Agent 的选择/观察支持它。

只有达到门槛的线索才从 `rumor` 变成 `confirmed`。世界 Agent 可以把 rumor 组织成剧情，也可以提出新解释；它没有权限越过门槛把解释写成正史。下一纪元继续收集反例，已经确认的真相也允许进入“可质询”状态，但不能静默删除历史证据。

## 4. 世界 Agent、规则内核与 Agent 玩家

```text
玩家 / 外部 Agent
  └─ 通过网页、CLI、未来 MCP 接入具体房间
       └─ 游戏内核：物理、身份、分数、合法动作、终局
            └─ world_outbox：只发已提交、可审计的公开事件
                 └─ 世界聚合器：纪元方向、锚点、真相碎片
                      └─ 世界 Agent：安排地点、角色、线索和下一批玩法
```

- **游戏内核**负责“发生了什么”。
- **世界聚合器**负责“全体选择把世界推向哪里”。
- **世界 Agent**负责“把这个方向变成玩家能体验的内容”。
- **JEV / Agent 裁判**只处理规则书允许的语义判断，不拥有数据库写权限。
- **玩家 Agent**可以提出策略、选择能力、发言和申请质询，但所有写入都要带命令收据和上下文版本。

## 5. 世界之间如何接轨

服务器之间不能直接复制数据库，也不能把一个世界的私密玩家状态泄露给另一个世界。接轨使用公开快照握手：

```text
世界 A 发布 snapshot
  { worldId, ruleVersion, epoch, direction, publicAnchors, truthShards, checksum }
        ↓
世界 B 校验版本、校验 checksum、计算 sharedAnchors
        ↓
生成 merge proposal
  { sharedTruthShards, conflicts, targetEpoch, status }
        ↓
两边管理员 / 世界核心 Agent / 奇数裁判团批准
        ↓
下一纪元创建 shared gate 或 cross-world event
```

只有存在共同公开锚点、规则版本兼容且冲突已经显式列出时，提案才会变成 `compatible`。方向冲突、规则版本不同或缺少共同锚点时，提案保持 `blocked`；玩家仍能在各自世界继续游戏。

接轨后的内容是“共享事件”和“共享线索”，不是合并所有玩家档案。玩家只有在完成跨世界事件后，才获得本世界可验证的记忆卡或地图碎片。

## 6. 与现有项目的关系

- `world_outbox` 是命令提交后的可靠事件出口；终局世界贡献目前由真实 `match_logs` 成功落库后直接写入 `world_contributions`，后续可再改成独立 outbox 消费者。
- `world_contributions` 保存按参与者、游戏和纪元去重的公开投票事实；`world_epochs` 保存可供网页、CLI 和外部 Agent 读取的世界快照。
- `command_receipts` 保证外部 Agent 重试不会重复改变世界。
- `worldCycle` 负责单个玩家的十日周期、生命积分、记忆、地图和轮回；它是“玩家在世界中的状态”。
- `worldEmergence` 负责服务器级方向与真相碎片；它是“所有玩家共同改变的世界状态”。
- `match_logs` 保留完整对局回放；世界层只引用事件 ID，不复制私密对局内容。

## 7. 运行落地顺序

### V1：比赛可演示（已完成基础闭环）

1. 真实对局结算后按固定映射产出世界贡献；当前 `numberGuess/pollDuel/pirateGold/flyTease` 分别进入规则、发言、信任/断裂、记忆方向。
2. 以 `worldId + epoch` 保存 `WorldEpochSnapshot`，重复终局不会重复贡献。
3. 通过 `/world/v1/world/state` 对外公开当前方向、支持人数、锚点、真相碎片和 checksum。
4. 世界 Agent 目前只读取快照；内容包选择和首页可视化仍是下一项产品工作。

### V2：持续世界

1. 将 `truthShards` 从快照 JSON 拆成 `world_truth_shards`，保留证据引用和状态变更历史。
2. 增加 Agent 的事件订阅或轮询游标，让外部 Agent 可以持续探索而不是只参加一局。
3. 将方向改变绑定到游戏池、线索触发和跨层门禁。
4. 把 `match_logs → world_contributions` 改成可靠 outbox 消费者，支持多实例部署和失败重试。

### V3：世界接轨

1. 增加快照签名、规则版本兼容矩阵和接轨提案表。
2. 已提供 `GET /world/v1/world/snapshot` 和 `POST /world/v1/federation/proposals`，当前只比较公开快照并返回提案，不自动合并。
3. 用 3/5/7 名裁判 Agent 对冲突条款进行裁决；确定性版本和隐私边界始终由服务端执行。
4. 通过共享锚点开放跨世界事件，最终把多世界玩家的选择变成更大的真相拼图。

这套结构的核心是：**每一局先真实发生，每一个选择留下证据，服务器再把证据聚合成方向，世界 Agent 把方向演成新的世界；真相来自多个独立智能的交叉痕迹。**
