# 终焉｜世界 Agent 运转与分布式裁判模型

> 目的：定义“元规则如何分发、游戏规则如何分发、外部 Agent 如何被召集为裁判，以及整个世界如何持续运行”。
>
> 结论：Agent 负责提议、编排、判断和叙事；世界内核负责权限、状态、胜负、账本和历史事实。

## 1. 不能只有一个总 Agent

如果让一个总 Agent 同时负责世界剧情、游戏状态、胜负和裁判，它会出现四个问题：

- 它可以私自改规则或改写结果。
- 玩家无法知道它依据的是哪一个版本的规则。
- 多个 Agent 无法独立验证同一事实。
- 一次模型异常会影响整个世界。

终焉采用三平面结构：

```text
┌─────────────────────────────────────────────┐
│ 参与者平面                                    │
│ 玩家 Agent / 内置 Agent / 外部裁判 Agent       │
│ 提交动作、提案、质询、裁判票和策略说明          │
└──────────────────────┬──────────────────────┘
                       │ 只能提交协议命令
┌──────────────────────▼──────────────────────┐
│ 世界控制平面                                  │
│ 世界编排、规则分发、裁判召集、叙事、观战、审计   │
│ 读取事件，提出下一步计划，不直接改共享状态       │
└──────────────────────┬──────────────────────┘
                       │ 经过验证的命令
┌──────────────────────▼──────────────────────┐
│ 确定性内核                                    │
│ 身份、权限、房间状态、规则校验、结算、账本、事件  │
│ 唯一能够写入共同世界事实                        │
└─────────────────────────────────────────────┘
```

Agent 可以分布式运行在玩家电脑、服务器、云函数或第三方平台，但所有写入都必须回到同一个世界内核。

## 2. 世界 Agent 角色

每个角色都有明确的输入、输出和权限。角色可以由不同模型或不同机器承担，也可以在演示时由同一进程托管多个角色；角色权限不能因此合并。

| 角色 | 主要工作 | 可以输出 | 不能做的事 |
|---|---|---|---|
| **周期时钟 Agent** | 推进世界周期、阶段和倒计时 | `cycle_tick`、阶段计划 | 直接决定玩家输赢 |
| **世界编排 Agent** | 根据历史事件安排房间、任务和叙事入口 | `world_intent`、任务候选、内容推荐 | 写入房间状态、跳过门禁 |
| **规则目录 Agent** | 管理规则包、版本、依赖和启用范围 | `rule_manifest`、校验报告 | 修改已发布规则或历史 |
| **房间主持 Agent** | 开房、补位、提示阶段、处理超时 | `room_command`、提醒 | 绕过游戏模块结算 |
| **裁判召集 Agent** | 按利益回避、能力和法定人数组建裁判团 | `judge_assignment` | 自己替所有裁判投票 |
| **证据审计 Agent** | 检查事件顺序、证据哈希和动作合法性 | `audit_report`、异常标记 | 直接改判已结算结果 |
| **叙事编年 Agent** | 将已确认事件写成世界记忆、旁白和章节 | `chronicle_entry`、旁白候选 | 把未发生的内容写成正史 |
| **奖励与成长 Agent** | 提出碎片、能力进化和解锁建议 | `reward_intent`、成长候选 | 直接发放超出账本的奖励 |
| **观战导演 Agent** | 从真实事件选择高光、镜头和音效 | `highlight_plan` | 创造不存在的事件 |
| **内容安全 Agent** | 检查文本、语音和玩家提交是否可展示 | `moderation_result` | 改写规则结算 |

其中“Agent”表示可替换的智能组件；实际的身份、权限、记账和结算仍由内核执行。

## 3. 元规则与游戏规则的分层

### 3.1 元规则

元规则是整个世界的宪法，首发阶段固定，不允许在普通对局中被改写：

1. 世界事实只能由确定性内核和版本化事件产生。
2. Agent 只能通过协议提交命令，不能直接写数据库。
3. 每个裁判团只能有 3、5 或 7 个有效席位。
4. 参与本局的席位不能担任本局裁判。
5. 核心胜负和计分条款不可质询。
6. 新判例只能从指定回合或下一局生效，不能追溯历史。
7. 事件日志追加写入，回放必须可复现。
8. 玩家密态信息不得通过观战、裁判或叙事接口泄漏给无权限席位。

### 3.2 游戏规则

游戏规则是某一内容包的局部规则，包括阶段、动作、信息可见性、状态变化、胜负、计分、可质询条款、证据格式、奖励和回放事件。

游戏规则可以在辩论类游戏中提出边缘条款修改，但必须经过元规则规定的流程，且只在未来范围生效。

## 4. 规则包的分发格式

规则不通过长提示词散发，而是以带版本和哈希的规则包分发：

```json
{
  "rulebookId": "rb-beast-race",
  "version": 3,
  "parentHash": "sha256:...",
  "scope": "game",
  "activation": "next_match",
  "metaRules": ["odd-quorum", "no-retroactive-ruling"],
  "clauses": [
    {
      "id": "race-c-021",
      "text": "雷云会使当前处于飞行状态的单位失去飞行并后退 5 格。",
      "kind": "effect",
      "appealable": true
    }
  ],
  "actions": "schema:beast-race/v1",
  "visibility": "schema:beast-race-view/v1",
  "judgeRubric": "rubric:rule-debate/v1",
  "signature": "ed25519:..."
}
```

分发时必须同时携带规则包 ID、版本、父版本、内容哈希、生效范围、不可质询条款、动作和视角 schema，以及裁判评分标准。

Agent 拿到的是“可执行说明书”，不是可以自行解释的散文。任何 Agent 返回的动作都要按同一规则包再次验证。

## 5. 规则发现与分发流程

### 5.1 发现

外部 Agent 首先读取世界目录：

```text
GET /world/v1/discovery
```

目录返回协议版本、当前周期、可加入的游戏和房间、可领取的 Agent 角色、可担任裁判的游戏，以及规则包的 ID、版本、哈希和能力要求。

### 5.2 下载

```text
GET /world/v1/rulebooks/{rulebookId}?version=3
```

客户端可以缓存规则包，但每次入局都要确认房间声明的版本和哈希。版本不一致时必须重新下载，不能自行拼接新旧条款。

### 5.3 入局绑定

加入房间后，服务端向玩家或 Agent 返回：

```text
matchId / defId / rulesetVersion / rulesetHash / seat / viewSchema / actionSchema
```

从这一刻起，所有动作都绑定这组版本信息。规则发生变更时只能产生新的规则快照和新的事件。

## 6. 辩论类游戏：专门的裁判召集场

“玄渊 · 规则辩论”是元规则与游戏规则的实验场，不负责替普通游戏随意改胜负。

### 6.1 一局流程

```text
展示当前规则书
  → 玩家 / Agent 提交边缘条款提案
  → 其他席位提出质询
  → 提案者回应
  → 裁判召集 Agent 发布裁判任务包
  → 外部 Agent 独立领取并投票
  → 3/5/7 票数聚合
  → 生成判例和下一版本规则快照
  → 从指定回合开始生效
```

### 6.2 裁判任务包

裁判 Agent 不直接读取整个房间，也不读取玩家私有提示词。它收到一个经过裁剪的证据包：

```json
{
  "assignmentId": "ja_01",
  "matchId": "m_01",
  "rulebookId": "rb-rule-debate",
  "rulebookVersion": 4,
  "clauseId": "race-c-021",
  "question": "该提案是否符合当前条款及其生效范围？",
  "proposal": { "operation": "clarify", "text": "..." },
  "evidence": [
    { "seq": 42, "type": "card_revealed", "payload": {} },
    { "seq": 43, "type": "tile_triggered", "payload": {} }
  ],
  "evidenceHash": "sha256:...",
  "rubric": ["事实一致性", "条款适配", "可执行性"],
  "deadline": "2026-09-23T12:00:00Z"
}
```

### 6.3 裁判 Agent 的返回

裁判必须返回结构化票：

```json
{
  "assignmentId": "ja_01",
  "decision": "accept",
  "confidence": 0.82,
  "clauseId": "race-c-021",
  "reason": "提案只澄清效果触发时点，没有改变基础胜负或历史结果。",
  "evidenceSeq": [42, 43],
  "bundleHash": "sha256:...",
  "idempotencyKey": "vote-..."
}
```

票据聚合规则：

- 只有来自有效 assignment、正确版本、正确证据哈希的票才计入。
- `accept / reject / partial` 采用多数票。
- 3、5、7 个有效票天然避免平票；无效或超时票必须记录。
- 达不到法定有效票数时，规则不生效，转入补充裁判或本地降级裁判。
- 裁判理由和引用事件进入回放，便于观众理解判决。

### 6.4 如何召集外部 Agent

1. Agent 通过公开协议声明 `judge` 能力和支持的游戏。
2. 裁判召集 Agent 排除本局参与者、同一 API Key 重复席位和利益冲突声明。
3. 按能力、延迟、信誉、近期负载和随机种子选择候选。
4. 给候选 Agent 发送相同证据哈希的任务包。
5. 候选 Agent 在截止时间内领取任务并回票。
6. 召集 Agent 只做席位编排和计票，不能替缺席裁判伪造理由。

首发演示可以使用一个固定裁判池，其中包括本地启发式、Jev 和外部 Agent；产品化后再加入信誉、质押、挑战和奖励。

## 7. 世界持续运转的事件循环

世界不是依靠一个 Agent 自由聊天，而是由事件循环驱动：

```text
Clock Tick
  → 读取上一事件和当前世界快照
  → 世界编排 Agent 提出候选任务 / 房间 / 叙事入口
  → 规则目录校验可用规则包
  → 房间主持 Agent 生成合法房间命令
  → 内核验证并写入事件
  → 裁判召集或游戏模块处理需要的下一步
  → 审计 Agent 检查事件链
  → 奖励 Agent 提出成长结果
  → 内核记账
  → 编年 Agent 写入可追溯世界记忆
  → 观战导演输出高光方案
```

只有“内核验证并写入事件”和“内核记账”是权威写操作，其余 Agent 都是候选生成器或审阅器。

## 8. 事件总线与状态边界

| 主题 | 内容 | 允许写入者 |
|---|---|---|
| `world.clock` | 周期、阶段、倒计时 | 内核时钟 |
| `world.rules` | 规则包发布、提案、判例、生效 | 规则内核 + 合法裁决 |
| `match.actions` | 玩家和 Agent 动作 | 房间运行时 |
| `match.rulings` | 裁判任务、票据、聚合结果 | 裁判协调器 + 内核 |
| `world.memory` | 奖励、成长、编年和高光索引 | 内核确认后的各 Agent |

任何 Agent 只能订阅自己需要的主题；裁判 Agent 只获得任务包中的证据，不拥有全局数据库查询权限。

## 9. 失败、作弊和恢复

- Agent 超时：记录 `judge_timeout` 或 `action_timeout`，按规则使用预先声明的替代流程。
- Agent 输出非法：保留原始响应摘要，拒绝写入，要求重新提交结构化票。
- 裁判意见冲突：使用多数票；不把模型平均概率当作胜负。
- 规则包版本冲突：拒绝动作，要求重新同步规则包。
- 事件写入失败：不发奖励、不推进阶段，使用幂等重试和状态快照恢复。
- 观战生成失败：保留原始事件，回放使用静态事件列表。
- 叙事 Agent 幻觉：只允许引用事件 ID，引用不存在的事件则审计失败。

## 10. 实现顺序

### 第一阶段：契约

- 增加规则包摘要、版本、激活范围和裁判任务包类型。
- 接通 discovery 和 rulebook 读取。
- 为 `GameAction`、`MatchEvent` 和 `Ruling` 增加版本绑定。

### 第二阶段：辩论裁判

- 建立固定裁判池注册、冲突回避、任务领取、结构化回票和多数聚合。
- 在规则辩论局完成一条“提案 → 质询 → 3 票裁决 → 下一回合生效”的整局烟测。

### 第三阶段：世界控制平面

- 将周期时钟、世界编排、规则目录、主持、审计、编年和观战导演接入事件总线。
- 每个角色先只输出候选命令和审计结果，由内核统一执行。

### 第四阶段：五个主游戏接入

- 先接入两个确定性游戏，再接入狼人杀、赛马和达芬奇密码。
- 每个游戏独立提供证据 schema 和是否需要裁判的说明。

## 11. 关键验收

完成这部分后，现场必须能看到：

1. Agent 读取到明确版本的规则包，而不是一段无版本提示词。
2. 两个 Agent 在规则辩论局中提出、质询和回应一条边缘规则。
3. 三个外部或内置裁判收到同一个证据哈希并独立回票。
4. 计票结果从事件中生成，并在下一回合生效。
5. 观众能看到裁判引用了哪些事件，玩家不能通过裁判席看到别人的密态。
6. 关闭 Jev 或外部 Agent 后，本地降级裁判仍能完成可复现结算。
