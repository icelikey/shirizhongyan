# 终焉｜游戏内容包与接入规范

> 当前项目不再按三人分工描述开发。所有工作按“公共底座、规则模板、体验内容、部署验收”四条工作流推进，最终由同一条主线收口。

## 1. 内容范围

首发只冻结五个主游戏：

- 青野算庭 · 猜平均数
- 红眼病 · 少数派票决
- 月影村 · 狼人杀
- 金壤 · 超能力赛马
- 金壤分潮 · 海盗分金

规则辩论是公共裁判流程；WASD 入界试炼是独立序章玩法。二者都不额外扩张主游戏数量。

每个游戏都必须在同一个房间运行时内完成：

```text
GameDefinition
  → GameModule
  → GameAction 校验
  → MatchState 推进
  → MatchEvent 记录
  → 玩家 / 观战投影
  → 结算 / 奖励 / 回放
```

## 2. 内容包最低文件

一个可发布内容包至少需要：

| 文件 / 模块 | 必须回答的问题 |
|---|---|
| `definition` | 名称、花色、席位、版本、门票、奖励、参与模式 |
| `rulebook` | 核心胜负、计分、可质询条款、阶段和时限 |
| `state` | 开局状态、跨轮字段、结束条件和 seed |
| `actions` | 真人和 Agent 能提交什么，什么动作非法 |
| `events` | 每个结果如何记录，谁能看见 |
| `projection` | 玩家、观众和裁判分别看到什么 |
| `replay` | 事件能否按同一版本重建同一结果 |
| `fallback` | AI、TTS、3D 或网络异常时如何继续 |
| `tests` | 纯规则、密态投影、重复请求、回放和整局烟测 |

只有提示词、卡牌图片或页面原型，没有状态推进和事件回放的内容，仍然是设计稿。

## 3. 五个内容包的接入重点

### 猜平均数与少数派票决

它们是公共 SDK 的基准模板。先保证范围、重复提交、超时、结算幂等、奖励回写和事件回放，再将同一套运行时提供给复杂游戏。

### 月影村狼人杀

身份、夜晚行动、白天发言、投票、胜负和密态必须由服务端管理。语音由 `SpeechProvider` 异步提供，失败时保留字幕；Jev 只做结构化判断，不直接写入胜负。

### 超能力赛马

复用 `contracts/beastRace.ts` 和 `beastRace.data.ts`，补齐模板执行器、跨轮 `matchState`、技能卡目标校验、格子事件、观战事件和回放。模型或 3D 资产不能决定数值结果。

### 海盗分金

采用 `pirateGold` 模板：提案人先提交按席位对齐的分配数组，存活席位看到提案后再投票。

- `matchState` 保存存活席位、当前提案人和金币总数；否决时只推进状态，不提前写入奖励。
- `pending` 投影只公开方案与已投票席位，`reveal` 才公开完整票面、出局和最终分配。
- 外部 Agent 使用统一 `GameAction` 的 `propose` / `vote`，不新增第二套 Gateway 协议。
- 观战重点是“提案 → 行贿 → 结盟/背叛 → 否决/封盘”的真实因果链。

## 4. 公共接口冻结

以下字段一旦进入整局联调，修改必须同时写迁移和回放兼容方案：

- `GameAction`
- `GameDefinition`
- `MatchEvent`
- `visibility` 与视角投影
- `defId`、`template`、`rulebookId`、`recordKey`
- 结算与奖励事件

赛马等复杂游戏可使用公共 `play` 动作和可选跨轮状态，但不能在页面内部定义另一套动作协议。

## 5. 合并与验收顺序

1. 先完成公共契约、Gateway、房间状态、事件记录和注册表。
2. 再完成确定性模板的回放和奖励验收，并把千轮猜数与海盗分金加入公开 Agent 演示。
3. 再接入狼人杀和赛马的规则模块；达芬奇密码保留为后续内容包候选。
4. 最后接入语音、3D、观战高光和营销展示。

所有内容包合并前至少通过：

```text
类型检查 → 纯规则测试 → 密态投影测试 → 回放测试
→ SDK 冒烟 → 真人 + Agent 整局脚本 → 构建与部署检查
```

详细目标和完成门槛以 [DEVELOPMENT-GOAL.md](../DEVELOPMENT-GOAL.md) 为准。
