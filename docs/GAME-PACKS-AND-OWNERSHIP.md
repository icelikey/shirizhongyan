# 黑客松小游戏内容包与三人协作分工

> 本文档定义黑客松首发的四个小游戏内容包、它们与公共运行时之间的契约，以及三人协作、接口冻结和合并规则。本文档只描述首发范围与可验证的交付边界。

## 1. 首发范围与状态口径

黑客松首发提供四个可独立开房、可由真人或外部 Agent 参加的小游戏：

1. **青野算庭 · 在线猜平均数**：当前已接入公共房间和 SDK，作为计算型首发游戏。
2. **红眼病 · 少数派票决**：当前已接入公共房间和 SDK，作为快速展示型首发游戏。
3. **玄渊 · 下一步规则辩论**：首发内容包，目标是展示结构化提案、质询与奇数裁判；在完成对应模板执行器和联调前，不标记为完成。
4. **金壤 · 超能力赛马**：首发内容包，已有赛马契约与数据基础；仍需接入模板执行器、事件演出和完整联机验收，不把契约或数据文件当作已完成的游戏。

**月影狼人杀不属于本次四个小游戏首发包。** 它保留为后续服务端化主线：身份、夜晚行动、白天发言、投票、密态投影、Jev 分析、语音和回放必须全部由服务端状态驱动，完成整局可复现验收后再单独发布。现有前端可玩或旧引擎代码不能作为“狼人杀已服务端化”的证据。

四个首发包共享一个房间、Gateway、Agent 注册、事件流、裁判、奖励和观战入口。每个游戏只新增自己的规则定义、模板模块、视图扩展和测试；不复制账号、房间或服务。

## 2. 公共内容包契约

### 2.1 内容包登记

每个官方内容包必须有稳定的 `defId` 和 `template`，并能被房间注册表解析为一个 `GameDefinition`。至少包含：

| 字段 | 要求 |
| --- | --- |
| `defId` | 永久稳定的内容包 ID，例如 `guess-core`、`poll-duel-core`、`rule-debate-core`、`beast-race-core` |
| `template` | 模板类型；公共运行时据此选择 `TemplateModule` |
| `version` | 规则或数据契约变更时递增；旧回放必须仍可解释 |
| `seats` | 席位数范围与默认值；不能由前端自行扩展 |
| `params` | 经 zod 或等价边界校验的静态参数 |
| `rulebookId` | 对应规则书；核心胜负和计分条款不可质询 |
| `recordKey` | 战绩写入键，版本升级不得无故改名 |
| `entryFee` / `rewards` | 由服务端计算和记账，前端只展示 |

公共 `TemplateModule` 负责以下边界：

- `normalizeSubmission`：把 `GameAction` 归一化为模板可处理的提交；自由文本不能直接成为合法动作。
- `timeoutFallback`：超时提交确定的兜底值，且必须可记录、可回放。
- `botPick`：内置 `echo-bot` 的合法动作选择。
- `resolveRound`：接收本轮结构化提交，返回事件、分数变化、下一轮状态和结束标志。
- `initMatchState`：只有需要跨轮状态的模板实现；猜平均数和票决可保持轻量状态，赛马必须实现。

所有结果写入统一事件流。事件至少包含 `matchId`、`defId`、`version`、`round`、`seq`、`actorSeat`、事件类型、公开载荷和必要的 `secret` 载荷。密态载荷只能在全知观战投影出现，玩家席位视图必须由服务端过滤。事件顺序是回放和高光集锦的唯一依据，视觉特效不能自行推导或改写结果。

公共动作保持向后兼容：

```ts
type GameAction =
  | { type: "start" }
  | { type: "submit"; value: number }
  | { type: "choose"; choice: number }
  | { type: "play"; cardId: string; targetSeat?: number };
```

其中 `play` 供赛马这类结构化、多字段卡牌动作使用。规则辩论当前先通过 `speak` 内承载的结构化 JSON 适配器验证模板逻辑，正式接入前仍需扩展共享动作契约和校验；不能在某个前端页面里私自增加动作形状。

## 3. 四个首发内容包

### 3.1 青野算庭 · 在线猜平均数

**玩法。** 每轮每个席位在定义的整数范围内同时提交一个数。服务端计算所有有效提交的平均数，再按规则计算目标值与各席位距离，近者得分；经过固定轮数后按累计得分排名。具体范围、轮数、目标倍率和奖励从 `params` 读取，不能由客户端计算结算结果。

**AI 价值。** 这是 level-k 推理的可见入口：Agent 需要估计其他 Agent 对平均数、对手策略层级和历史结果的预期。观众能通过每轮提交、平均值、目标值和距离看到“猜别人会怎么猜”的递进过程。AI 的解释文本可以作为旁白或高光说明，但不参与计分。

**可视化。** 以数轴和分布带显示合法范围、各席位提交点、平均数、目标线和最终距离；揭晓前隐藏提交点，揭晓后按统一顺序翻开。回放至少展示“提交 → 平均数 → 目标值 → 得分”的因果链。

**数据契约。**

- 模板：`numberGuess`；已存在的 `guess-core` 保持兼容。
- 参数：`rounds`、`min`、`max`、目标倍率、计分参数；全部在 `GameDefinition.params` 中校验。
- 动作：`submit.value`，必须是整数且落在定义范围内。
- 每轮提交：`{ seat, value, order }`；服务端补齐 `round`、`submittedAt` 和结算事件。
- 揭示事件：平均数、目标值、每席距离、每席得分和累计得分；未揭晓前不泄漏其他席位的值。

**完成判据。**

- 真人、外部 Agent、`echo-bot` 均能通过同一 Gateway 入座、观测、提交并完成一局。
- 非法范围、重复提交、超时提交和重复结算都有服务端结果，且不会改变其他席位状态。
- 至少一条公共事件流能够完整回放一局，回放计算出的排名与结算记录一致。
- 前端展示提交、揭晓和结果三阶段；`pnpm check`、相关模板测试和现场演示命令通过。

当前状态：**已联机，可作为首发基准模板；仍以现场整局烟测作为最终证据。**

### 3.2 红眼病 · 少数派票决

**玩法。** 每轮所有席位同时从给定选项中选择一个。选择人数最少且唯一的选项为本轮少数派，选择它的席位得分；最少人数并列时本轮无人得分。固定轮数结束后按累计得分排名。

**AI 价值。** 它把“选自己认为会赢的选项”压缩成观众能在 30 秒内理解的群体博弈。Agent 要判断选项吸引力、其他席位的趋同风险和历史偏好；人类的突然反直觉选择也会立刻改变少数派分布。

**可视化。** 投票前展示选项卡和倒计时，不显示任何席位选择；揭晓时同时翻开选择并显示柱状计数，唯一少数派使用高亮，平票使用明确的“无人得分”状态。每轮保留上一轮分布，便于观众看出策略迁移。

**数据契约。**

- 模板：`pollDuel`；已存在的 `poll-duel-core` 保持兼容。
- 参数：`rounds` 和有序 `choices[]`；选项标签是展示数据，结算使用选项下标。
- 动作：`choose.choice`，必须是 `0..choices.length-1` 的整数。
- 揭示事件：`{ round, counts, minorityChoice, tied, scores, cumulativeScores }`；`counts` 在揭示前不可进入玩家投影。
- 服务端固定“唯一最少才得分”的规则，前端不能根据展示结果重复计算奖励。

**完成判据。**

- 真人、外部 Agent 和 `echo-bot` 可以完成多轮同时票决。
- 非法选项、超时、重复提交、最少并列和正常少数派均有测试覆盖。
- 观众可以清楚看到选项、计数、少数派和平票结果，且玩家视角看不到未揭示选择。
- 一局结束后累计分数、奖励和事件回放一致；公共检查和 SDK 冒烟通过。

当前状态：**已联机，可作为首发基准模板；仍以现场整局烟测作为最终证据。**

### 3.3 玄渊 · 下一步规则辩论

**玩法。** 每局围绕一个原创、边界清楚但存在解释空间的议题进行多轮辩论。席位先提交结构化规则提案，再按顺序对其他提案进行质询，提案者提交回应，最后由不参加本局的奇数裁判团裁定采纳、驳回或部分成立。获采纳的规则只影响后续回合或下一局，不追溯改写已结算结果；最终由规则书规定的票决和计分条款结束对局。

**AI 价值。** 这个包展示 Agent 是否能读懂条款、发现边界、提出可执行修订并针对对方论证回应。Jev 只输出结构化判断或从候选项中选择，不直接替玩家写出合法规则；自由文本只能作为提案的说明字段，必须先归一化、校验并绑定条款 ID。

**可视化。** 页面同时呈现当前规则书、提案差异、质询链和裁判席。每个提案显示“原条款 → 修改点 → 影响范围”，质询沿时间线连接到被质询句段；裁判票逐席翻开，最后生成一张本局有效版本的规则快照。观众可看到全部提案，玩家只能看到公共条款和自己允许观测的密态信息。

**数据契约。**

- 模板建议：`ruleDebate`，注册到公共 `TemplateModule`，不得另起服务。
- 动作：`play` 携带结构化 `proposalId`、`clauseId`、`operation`、`argument` 或 `targetSeat`；服务端校验提案阶段、条款可修改性、长度和席位权限。
- 状态：当前 `rulebookId`、版本、提案集合、质询状态、回应状态、裁判席和裁定结果；每次规则变化生成不可变版本号。
- 事件：`proposal_submitted`、`challenge_opened`、`response_submitted`、`ruling_cast`、`rule_version_accepted`、`round_settled`。
- 裁判：只能使用 3、5 或 7 席，裁判不得是本局参与者；核心胜负和计分条款不可质询。

**完成判据。**

- 一局能完成“展示议题 → 提案 → 质询 → 回应 → 奇数裁判 → 应用下一步规则 → 结算”。
- 服务端拒绝越权改核心条款、修改历史版本、重复投票、非当前阶段动作和无效 `clauseId`。
- Jev 不可用时，本地启发式仍能完成裁判流程；Jev 的输出不绕过规则校验。
- 事件流能重放出同一规则版本和同一结算；观战页能区分公共条款、席位密态和裁判信息。
- 至少有一条真人 + Agent 的现场脚本跑通，并有结构化事件与截图或录屏证据。

当前状态：**首发目标，待实现和联调；不得把规则书、裁判契约或 UI 原型写成已完成。**

### 3.4 金壤 · 超能力赛马

**玩法。** 开局各席位选择一只具有不同移动特性和克制关系的动物，并获得自己的技能手牌。每轮从合法手牌中选择一张，可在需要时指定目标；服务端同时揭示并按固定优先级结算位移、状态、格子事件和反制。先到终点者获胜。技能卡只改变位移、信息或状态，不改写“先到终点者胜”的基本判定。

**AI 价值。** 它把“选择流派、保留手牌、选择目标、预判格子”叠成可复盘的因果链。Agent 的每轮决策可以从合法候选集合中选择，减少自由文本和延迟；LLM 或 Jev 可用于赛前策略宣言、候选评分或赛后解释，不能直接提交未经校验的卡牌效果。

**可视化。** 赛道显示位置、格子类型、动物状态和剩余手牌；每轮按“全部扣牌 → 逐张翻牌 → 卡牌命中 → 格子触发 → 位移与状态变化”的顺序演出。观众必须能看懂例如“鹤飞行 → 雷云击落 → 退格 → 反击”的完整事件链。缺少 3D 资产时使用 2D 卡面和 CSS 动效，视觉层不能修改数值结果，并支持 `prefers-reduced-motion`。

**数据契约。**

- 模板建议：`beastRace`；复用 `contracts/beastRace.ts` 与 `beastRace.data.ts`，通过 `TemplateModule` 接入。
- 动作：`play { cardId, targetSeat? }`；服务端校验卡牌属于该席位、当前仍在手牌、目标合法、冷却和阶段均有效。
- 初始状态：由匹配 seed 生成固定赛道格子、动物选择、位置、状态、手牌和回合上限；同一 seed 必须能重放。
- 卡牌：每兽 8 张，按疾行、扰行、御守、反照分类；卡牌效果记录为结构化 delta，不接受客户端传入数值效果。
- 事件：`beast_selected`、`card_committed`、`card_revealed`、`tile_triggered`、`movement_applied`、`status_changed`、`race_finished`。
- 运行时必须实现跨轮 `matchState`；100 格或其他赛道长度以冻结后的内容数据为准，不能在 UI 中临时改为另一套长度。

**完成判据。**

- 真人、外部 Agent 和 `echo-bot` 能完成一局；赛道、手牌、目标和状态由服务端校验。
- 赛马核心契约测试覆盖卡牌数量、合法目标、克制关系、格子效果、反制顺序和先到终点判定。
- 至少跑通一条可解释的飞行、雷云击落、位移和反击事件链，并能在观战回放中逐事件复现。
- 断线、超时、重复出牌和无效目标不会破坏跨轮状态；结束状态和奖励只产生一次。
- 赛道视图有静态降级展示，动效可关闭；模板测试、前端检查和现场整局脚本通过。

当前状态：**首发目标，契约和数据已有基础，执行器、演出与完整联机验收未完成。**

## 4. 长期内容包扩展方式

长期新增内容包必须沿用以下顺序：

1. 先写规则书、状态机、动作和事件清单，明确哪些信息公开、哪些信息密态，以及胜负和计分条款。
2. 在 `contracts/` 增加版本化类型和边界 schema；若是复杂游戏，先扩展通用 `GameAction`、`RoundEntry.payload` 或 `initMatchState`，并为旧模板保留可选兼容路径。
3. 以 `TemplateModule` 实现服务端归一化、合法性校验、超时兜底、状态推进、结算和回放事件。
4. 在注册表登记 `defId`、模板、规则书、座位范围、参数和奖励；前端根据房间视图渲染，不复制规则。
5. 增加纯规则测试、SDK 冒烟、密态投影测试、回放测试和至少一条真人 + Agent 场景脚本。
6. 最后增加观战演出和内容资产。资产缺失时必须有 2D 或静态降级，视觉不能成为服务端结算依赖。

内容包可以通过参数和数据文件扩展议题、赛道、选项、卡牌、规则书版本和奖励，但不能用配置绕过三条基础铁律：卡牌不直接改胜负数值，异能只改变信息或时间，密态事件只进入全知观战投影。新内容包不得复制成独立账号、独立房间服务或独立裁判服务。

## 5. 三人模块分工

### A 号：公共平台与协议

建议分支：`codex/platform-cloud`。

负责 Gateway、公开 Agent 注册、CLI、房间运行时、注册表、数据库持久化、事件流、部署与 CI，以及所有公共契约的向后兼容。A 号维护 `contracts/` 的共享类型、`api/games/sdk/runtime.ts`、`registry.ts` 和内容包接入骨架。

交付判据：四个模板都能被注册表发现；动作、座位、超时、奖励和事件落库有统一入口；健康检查、构建、CLI 检查和部署检查通过；仓库不含 Key、密码或真实邀请码。

### B 号：规则模板与 AI 裁判

建议分支：`codex/game-templates`。

负责四个内容包的服务端规则：猜平均数和少数派票决的维护与扩展、规则辩论模板、超能力赛马执行器、规则书、Jev 结构化决策、裁判团和纯规则测试。B 号不能在模板内直接写数据库副作用，也不能让 LLM 输出绕过 `GameAction` 校验。

交付判据：每个模板能从输入状态得到确定的下一状态和事件；相同 seed、版本和提交能重放相同结算；非法动作、超时和重复请求有测试；Jev 失败有本地降级路径。

### C 号：观战、视觉与内容验收

建议分支：`codex/content-spectator`。

负责四个游戏的房间入口、玩家操作、观战投影、分阶段揭示、结果卡、高光集锦、静态降级和现场演示脚本。C 号只能消费服务端房间视图和事件，不能在前端决定身份、胜负、隐藏信息或奖励。

交付判据：观众能看懂每个游戏的“提交/提案 → 揭示/裁判 → 结果”因果链；玩家视角和全知观战视角不混淆；动效关闭后仍能完成操作；四个现场脚本有可复查的截图、录屏或事件回放。

### 狼人杀的边界

狼人杀不分配到本次四个首发包的完成承诺。后续服务端化时由 B 号负责状态机与规则，A 号负责公共密态投影、事件和 Gateway 兼容，C 号负责观战、语音和引导；必须另开任务卡，完成整局服务端烟测后再进入首发之外的发布评审。

## 6. 分支、PR、接口冻结与合并

### 分支规则

- 所有人从最新 `main` 建分支，不直接推送 `main`。
- 一个分支只承载一个模块或一组相互依赖的内容包变更；不要把部署、规则、视觉和无关清理混在同一个 PR。
- 分支名使用 `codex/` 前缀；提交信息写清行为变化，例如 `feat: add rule debate template`。
- 修改前先确认当前 `main` 已包含依赖 PR；有冲突时先同步并在本分支解决，不在合并按钮里临时猜测规则。

### PR 必填内容

每个 PR 必须写清：目标、改动文件、公共接口变化、数据或迁移影响、验收命令、现场场景、截图或录屏、已知限制。涉及内容包时，还要附 `defId`、模板、规则书版本、动作样例和事件样例。

### 接口冻结

以下内容进入首发联调后冻结：

- `GameAction`、`GameDefinition`、`TemplateModule` 的公共字段和错误语义；
- 房间视图、密态投影、事件基本字段和事件顺序；
- `defId`、`template`、`rulebookId`、`recordKey` 和已发布参数含义；
- 结算、奖励、回放和 `secret` 过滤规则。

冻结后若确需改动，必须先开接口变更 PR，写出旧调用方、迁移方式、回放兼容策略和新增测试；A 号批准契约，B 号验证规则，C 号确认视图和演示仍可用。未经三方在 PR 中明确回复，不能合并破坏性变更。

### 合并顺序与门禁

依赖顺序固定为：

1. A 号先合并公共契约、运行时、事件和注册表骨架；
2. B 号在契约冻结版本上合并模板、规则书和测试；
3. C 号在服务端视图和事件样例稳定后合并页面、演出和现场脚本；
4. 三人共同做四个游戏的整局联调，A 号收口发布分支。

合并前至少执行：

```bash
cd app
pnpm check
pnpm test
pnpm build
cd ../cli
npm run check
```

若数据库、Jev、TTS 或网络不可用，必须验证对应降级路径；降级通过不等于主路径完成。任何一个内容包缺少服务端结算、事件回放或现场整局证据，都只能标记为“进行中”，不能在 README、演示脚本或发布说明中写成已完成。
